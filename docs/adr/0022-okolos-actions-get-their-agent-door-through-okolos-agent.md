# ADR-0022. Действия Okolos получают дверь для агента через Okolos Agent, тремя классами глаголов

**Дата:** 2026-11-18
**Статус:** принято агентом по делегированию оператора (правила «полная делегация», 2026-11-05 и
2026-11-08: решение, которое оператор не принимал сам, принимается по его записанным решениям, цели
проекта и самому безопасному обратимому варианту). Пересматривается, когда построен K3 (B-142).
**Основание:** решение оператора 2026-11-07 (сессия Claude Code `12c8d3fa`, проект fabric-agents-database):
«любое действие в интерфейсе должно уметь делаться клауд кодом по моему запросу»; DEC-0121; строка
B-218 в `docs/backlog.md`; поле «Agent door (B-218)» у каждого экрана в `docs/ux/screens.md`.

## Контекст

У Okolos 22 экрана, и почти ни у одного действия нет двери для агента: сегодня есть только HTTP
публичного воркера (SCR-14: `GET /status/domain`, `POST /appeal`) и CLI проверки письма
`okolos-mail` (SCR-21, SCR-22). Три ограничения, уже записанные в этом репозитории:

- **В Okolos нет `nativeMessaging` и `externally_connectable`** (ADR-0018, `tools/manifest.test.ts`),
  так что ни агент, ни демон не могут сами позвать расширение.
- **Дверь Okolos Agent в Б1 не принимает браузер клиентом**: Streamable HTTP только на
  `127.0.0.1:47871`, любой `Origin` или `Sec-Fetch-*` отвергается (спека Б1, REQ-57, ветка
  `bridge/b1-run2`).
- **Часть действий останавливает самого агента**: «Разрешить один раз» (SCR-06), «Всё равно
  продолжить» (SCR-05, SCR-19), «Это неверно» и восстановление скрытого текста (SCR-03, SCR-04).
  Дверь к ним, открытая тому агенту, которого они держат, снимает ворота руками того, кого они держат.

## Решение

1. **Одна дверь: MCP Okolos Agent.** Никакого второго сервера и никакого CLI поверх данных
   расширения. Агент уже будет привязан к демону (Б1); действия Okolos становятся глаголами той же
   двери, с тем же журналом и той же привязкой.
2. **Расширение подключается к демону само, изнутри.** Фон Okolos открывает соединение к
   `127.0.0.1` по отдельному маршруту демона, после того как человек привязал Okolos в его панели
   (токен в `chrome.storage.local`). Это единственный путь, при котором расширение не получает
   новых прав: `nativeMessaging` и `externally_connectable` не появляются, `tools/manifest.test.ts`
   не меняется. Маршрут и его проверки (токен, `Host`, отказ любому другому `Origin`) пишутся в
   спеке фазы, которая его строит, не в Б1.
3. **Три класса глаголов.**
   - **Чтение**: вердикт текущей страницы, очередь, журнал, самоаудит, расширения, утечки (без
     адреса почты), выгрузка данных. Открыто привязанному агенту.
   - **Обратимые действия над своими настройками**: список брендов, тихий режим, прокси, срок
     хранения, «Убрать из доверенных», «Отметить решённым», «Это изменение в порядке». Открыты
     привязанному агенту, каждое в журнале с его `agentId`.
   - **Ворота и необратимое**: «Разрешить один раз», «Всё равно продолжить», «Это неверно»,
     восстановление скрытого текста; удаление всех данных и очистка хранилища. Агент только
     **просит**: Okolos показывает запрос на своей поверхности (закрытый корень тени, канал, который
     агент не подделает) и выполняет его по нажатию человека; удаление идёт через
     `fabric_effect_request`. Ключ HIBP и пароли остаются людскими воротами.
4. **Порядок волн**: (а) K3 и маршрут расширения; (б) чтение и выгрузка; (в) обратимые действия;
   (г) запросы на ворота. Каждая волна: строки в `docs/backlog.md` и поле «Agent door» у экранов.

## Цена

- **До K3 у Okolos нет двери для агента**, кроме SCR-14 и `okolos-mail`. Решение не обещает раньше.
- **Новое исходящее соединение фона**, хоть и на loopback: оно попадёт в реестр назначений
  (`packages/net/src/destinations.ts`) и в журнал отправок, как любое другое, и `docs/privacy.md`
  назовёт его до первой сборки с ним.
- **Ворота медленнее для агента**: каждый запрос третьего класса ждёт человека. Это и есть смысл.
