# Подпись фидов — раннбук

Расширение принимает обновление фида только с подписью Ed25519, проверенной
ключом, **вкомпилированным в сборку**. Ключ, доставленный по тому же каналу,
что и фид, не защищает ни от чего: кто может подменить одно, подменит и второе.
Поэтому смена ключа — это релиз, намеренно.

## Где что лежит

| Половина | Где | Права |
|---|---|---|
| Публичная (32 сырых байта, base64) | `apps/extension/src/background/feeds.ts` → `FEED_PUBLIC_KEY` | в репозитории, так и задумано |
| Приватная (PKCS8 PEM) | `~/.okolos/feed-signing-key.pem` на машине издателя | `0600`, каталог `0700` |
| Публичная в PEM, для удобства | `~/.okolos/feed-signing-key.pub` | `0644` |

Приватной половины нет и не должно быть ни в репозитории, ни в CI-логах, ни в
переменных окружения, которые печатаются. `tools/feed-key.test.ts` проверяет это
по **содержимому** всех отслеживаемых файлов, а не по имени: приватный ключ,
закоммиченный как `notes.txt`, — всё ещё приватный ключ.

## Подписать обновление

```bash
node tools/sign-feed.mjs update.json > signed.json
node tools/sign-feed.mjs --check signed.json   # проверить тем ключом, что уедет в сборку
```

Ключ читается из `OKOLOS_FEED_KEY` (PKCS8 PEM целиком) или, если её нет, из
`~/.okolos/feed-signing-key.pem`. В CI — только через секрет, никогда из файла
в репозитории.

Инструмент импортирует `serialiseUpdate` из того же исходника
`packages/core-feeds/src/apply.ts`, который компилируется в расширение. Это не
обещание «мы будем держать их в синхроне» — это один файл на обе стороны.

## Сгенерировать новую пару (ротация)

```bash
node -e '
const { generateKeyPairSync } = require("node:crypto"), fs = require("fs"), os = require("os"), p = require("path")
const { publicKey, privateKey } = generateKeyPairSync("ed25519")
const raw = Buffer.from(publicKey.export({ format: "jwk" }).x, "base64url")
const dir = p.join(os.homedir(), ".okolos")
fs.mkdirSync(dir, { recursive: true, mode: 0o700 })
fs.writeFileSync(p.join(dir, "feed-signing-key.pem"), privateKey.export({ type: "pkcs8", format: "pem" }), { mode: 0o600 })
console.log("FEED_PUBLIC_KEY =", raw.toString("base64"))'
```

Затем: вписать напечатанное в `FEED_PUBLIC_KEY`, выпустить релиз, и только
после того как он раскатился — начать подписывать новым ключом. Порядок
обратный ломает обновления у всех, кто ещё на старой сборке.

Скрипт выше **перезапишет** существующий приватный ключ. Ротация — это
осознанное действие: сначала убедись, что старый ключ больше не нужен для
подписи ничего, что ещё в обращении.

## Что проверяется автоматически

`tools/feed-key.test.ts`, восемь правил:

- `FEED_PUBLIC_KEY` — не плейсхолдер и не пустая строка;
- это ровно 32 байта в base64 — форма, которую принимает `importKey("raw", …)`;
- Node может его импортировать (проверка слабая: 32 байта `0xff` тоже
  импортируются, потому что принадлежность точки кривой не проверяется — по
  сути ключ доказывает следующее правило);
- инструмент подписывает то, что этот ключ принимает — пара сходится;
- подпись любым другим ключом отвергается;
- индекс git прочитан (пустой список не сойдёт за чистое дерево);
- ни один отслеживаемый файл не содержит PEM-заголовка приватного ключа;
- `.gitignore` закрывает `*.pem` и `*.key`.

## Опубликовать фид

```bash
pnpm feed:refresh                                          # собрать, подписать, загрузить, проверить — из чекаута на origin/main
node tools/publish-feed.mjs ~/.okolos/state/feeds/phishing.json             # только подписать → загрузить → проверить живое
node tools/publish-feed.mjs ~/.okolos/state/feeds/phishing.json --dry-run   # всё, кроме загрузки
pnpm feed:snapshot                                         # перенести опубликованное в feeds/phishing.json — для коммита
```

**Исходник фида живёт вне рабочего дерева** — `~/.okolos/state/feeds/phishing.json` на машине
издателя ([ADR-0017](../adr/0017-the-feed-agent-publishes-from-a-pinned-checkout-and-counts-from-what-is-served.md)).
Опубликованное тело по-прежнему обязано иметь дом, из которого его можно переиздать не
вспоминая, — но этим домом был отслеживаемый `feeds/phishing.json`, и агент переписывал его
каждый прогон. Дерево было вечно грязным, а любая рутинная команда git (`checkout -- .`,
`stash`, `reset`) откатывала счётчик версий: на 2026-10-03 в дереве v51, в HEAD v42, и
следующий прогон опубликовал бы v43, которую каждое расширение с v51 отвергло бы как повтор.
Теперь отслеживаемый файл — закоммиченный снимок: затравка для новой машины и запасной вход
гейта выпуска на CI. Обновляется он только намеренно, `pnpm feed:snapshot` и коммитом.

**Версия берётся у воркера.** Сборка читает `/feeds/phishing` и ставит
`max(отданная, локальная, снимок) + 1`; публикация отказывает, если версия не выше отданной, а
та же версия с теми же байтами — это повтор уже прошедшей публикации, и он принимается без
второй загрузки. Воркер недоступен — сборка отказывает, а не угадывает.

**wrangler закреплён** в `apps/proxy` (devDependency) и вызывается через
`pnpm --config.verify-deps-before-run=false exec wrangler`: без этого флага `pnpm exec` ставит
недостающую зависимость перед запуском (проверено 2026-10-03), то есть ходил бы в реестр с
токеном D1 в окружении. Телеметрия wrangler выключена (`WRANGLER_SEND_METRICS=false`).

## Агент обновления

```bash
pnpm feed:agent                                        # чекаут агента, plist, загрузка
node tools/install-feed-agent.mjs --status             # plist, состояние launchd, последний прогон
node tools/install-feed-agent.mjs --uninstall          # bootout, удалить plist, проверить launchctl print
node tools/install-feed-agent.mjs --uninstall --purge  # и чекаут, состояние, логи
```

- **Где работает:** собственный чекаут `~/.okolos/agent-checkout` (detached worktree на
  `origin/main`); перед каждым прогоном агент перематывает его на `origin/main` и, если
  сдвинулся lockfile, ставит только инструменты публикации. Ручной `pnpm feed:refresh` из
  клона не на `origin/main` отказывает; `--unpinned` — аварийный обход, он записывается в статус.
- **Когда:** каждые 12 часов и при входе в систему; при входе прогон смотрит на возраст
  отданного фида и, если тот моложе 11 часов, записывает «skipped» и выходит.
- **Границы:** каждая стадия — дочерний процесс в своей группе с дедлайном; весь прогон —
  под сторожем на 30 минут; один прогон за раз (`~/.okolos/state/feed.lock`, общий с ручным
  запуском); три попытки с паузами 30 с и 2 мин.
- **Где смотреть:** лог `~/Library/Logs/Okolos/feed.log` (5 × 5 МБ, `0600`), статус
  `~/.okolos/state/feed-status.json` — `outcome`, `stage`, `exit`, `version`, `entries`,
  `consecutiveFailures`, `lastPublished`. Две неудачи подряд или `lastPublished` старше 26 часов —
  повод разбираться.
- **Токен** получает только стадия публикации: раннер секрета (`OKOLOS_SECRET_RUNNER` в plist,
  argv без значения) оборачивает её одну.

Входной файл — обновление без подписи:

```json
{ "kind": "snapshot",
  "body": { "name": "phishing", "version": 1, "updatedAt": "2026-08-08T00:00:00.000Z",
            "entries": ["evil.test"] } }
```

Одна команда намеренно: **таблица фидов оставалась пустой именно потому, что
публикация была фразой в раннбуке.** Шаг, который делают руками, — это шаг,
который пропускают, когда поздно. Инструмент подписывает через
`tools/sign-feed.mjs` (не переписывая его), проверяет подпись **тем ключом,
который уедет в сборку**, кладёт в D1 и в конце скачивает опубликованное с
воркера, сверяя байт в байт.

**Воркер не подписывает никогда.** Приватная половина ключа на сервер не
попадает: он отдаёт ровно то, что было опубликовано, и любое изменение по пути
провалило бы проверку в расширении — в этом и смысл.

**Публикация пишет обе таблицы.** `feeds` — то, что скачивает и на чём
блокирует расширение; `listings` — то, из чего отвечает публичная страница
статуса. Написанные порознь, они разошлись: воркер отдавал фид с четырьмя
доменами и о каждом из них отвечал владельцу «ничего не записано». Теперь это
один SQL-файл и одна операция, а смоук в конце спрашивает страницу о первом
домене фида и требует ответа `listed` — публикация, которая не может ответить
за опубликованное, не закончена.

Правила, которые держит `tools/listings.mjs` (тесты — `tools/listings.test.ts`):
снимок выметает то, что фид больше не несёт, дельта не трогает то, о чём молчит;
листинг заводится по хосту, даже если запись сужена путём; `entry_date` — дата,
а не мгновение, и она не переписывается при переиздании, потому что её цитирует
владелец.

**Версию надо повышать.** Расширение отвергает обновление, которое не новее
того, что уже в силе (`not-newer`), — это защита от повтора, а не придирка.

Проверено 2026-08-08 сквозным прогоном: опубликованный фид скачан с воркера,
проверен ключом из `feeds.ts` и принят `applyUpdate` — v1, 4 записи.
