# Подпись фидов — раннбук

Расширение принимает обновление фида только с подписью Ed25519, проверенной
ключом, **вкомпилированным в сборку**. Ключ, доставленный по тому же каналу,
что и фид, не защищает ни от чего: кто может подменить одно, подменит и второе.
Поэтому смена ключа — это релиз, намеренно.

## Где что лежит

| Половина | Где | Права |
|---|---|---|
| Публичная (32 сырых байта, base64) | `apps/extension/src/background/feeds.ts` → `FEED_PUBLIC_KEY` | в репозитории, так и задумано |
| Приватная (PKCS8 PEM) | `~/.okolos/feed-signing-key.pem` на машине издателя | `0600`, каталог `0700` |
| Публичная в PEM, для удобства | `~/.okolos/feed-signing-key.pub` | `0644` |

Приватной половины нет и не должно быть ни в репозитории, ни в CI-логах, ни в
переменных окружения, которые печатаются. `tools/feed-key.test.ts` проверяет это
по **содержимому** всех отслеживаемых файлов, а не по имени: приватный ключ,
закоммиченный как `notes.txt`, — всё ещё приватный ключ.

## Подписать обновление

```bash
node tools/sign-feed.mjs update.json > signed.json
node tools/sign-feed.mjs --check signed.json   # проверить тем ключом, что уедет в сборку
```

Ключ читается из `OKOLOS_FEED_KEY` (PKCS8 PEM целиком) или, если её нет, из
`~/.okolos/feed-signing-key.pem`. В CI — только через секрет, никогда из файла
в репозитории.

Инструмент импортирует `serialiseUpdate` из того же исходника
`packages/core-feeds/src/apply.ts`, который компилируется в расширение. Это не
обещание «мы будем держать их в синхроне» — это один файл на обе стороны.

## Сгенерировать новую пару (ротация)

```bash
node -e '
const { generateKeyPairSync } = require("node:crypto"), fs = require("fs"), os = require("os"), p = require("path")
const { publicKey, privateKey } = generateKeyPairSync("ed25519")
const raw = Buffer.from(publicKey.export({ format: "jwk" }).x, "base64url")
const dir = p.join(os.homedir(), ".okolos")
fs.mkdirSync(dir, { recursive: true, mode: 0o700 })
fs.writeFileSync(p.join(dir, "feed-signing-key.pem"), privateKey.export({ type: "pkcs8", format: "pem" }), { mode: 0o600 })
console.log("FEED_PUBLIC_KEY =", raw.toString("base64"))'
```

Затем: вписать напечатанное в `FEED_PUBLIC_KEY`, выпустить релиз, и только
после того как он раскатился — начать подписывать новым ключом. Порядок
обратный ломает обновления у всех, кто ещё на старой сборке.

Скрипт выше **перезапишет** существующий приватный ключ. Ротация — это
осознанное действие: сначала убедись, что старый ключ больше не нужен для
подписи ничего, что ещё в обращении.

## Что проверяется автоматически

`tools/feed-key.test.ts`, восемь правил:

- `FEED_PUBLIC_KEY` — не плейсхолдер и не пустая строка;
- это ровно 32 байта в base64 — форма, которую принимает `importKey("raw", …)`;
- Node может его импортировать (проверка слабая: 32 байта `0xff` тоже
  импортируются, потому что принадлежность точки кривой не проверяется — по
  сути ключ доказывает следующее правило);
- инструмент подписывает то, что этот ключ принимает — пара сходится;
- подпись любым другим ключом отвергается;
- индекс git прочитан (пустой список не сойдёт за чистое дерево);
- ни один отслеживаемый файл не содержит PEM-заголовка приватного ключа;
- `.gitignore` закрывает `*.pem` и `*.key`.

## Опубликовать фид

```bash
pnpm feed:refresh                                          # собрать, подписать, загрузить, проверить — из чекаута на origin/main
node tools/publish-feed.mjs ~/.okolos/state/feeds/phishing.json             # только подписать → загрузить → проверить живое
node tools/publish-feed.mjs ~/.okolos/state/feeds/phishing.json --dry-run   # всё, кроме загрузки
pnpm feed:snapshot                                         # перенести опубликованное в feeds/phishing.json — для коммита
```

**Исходник фида живёт вне рабочего дерева** — `~/.okolos/state/feeds/phishing.json` на машине
издателя ([ADR-0017](../adr/0017-the-feed-agent-publishes-from-a-pinned-checkout-and-counts-from-what-is-served.md)).
Опубликованное тело по-прежнему обязано иметь дом, из которого его можно переиздать не
вспоминая, — но этим домом был отслеживаемый `feeds/phishing.json`, и агент переписывал его
каждый прогон. Дерево было вечно грязным, а любая рутинная команда git (`checkout -- .`,
`stash`, `reset`) откатывала счётчик версий: на 2026-10-03 в дереве v51, в HEAD v42, и
следующий прогон опубликовал бы v43, которую каждое расширение с v51 отвергло бы как повтор.
Теперь отслеживаемый файл — закоммиченный снимок: затравка для новой машины и запасной вход
гейта выпуска на CI. Обновляется он только намеренно, `pnpm feed:snapshot` и коммитом. С B-158 этот
коммит делает агент: после публикации он открывает или обновляет PR со снимком, когда снимку на
`main` 7 дней или больше (ниже, «Снимок в дереве»). Пока оператор не решил B-186, этот PR сливает
человек; руками снимок коммитят, только если PR агента нет.

**Версия берётся у воркера.** Сборка читает `/feeds/phishing` и ставит
`max(отданная, локальная, снимок) + 1`; публикация отказывает, если версия не выше отданной, а
та же версия с теми же байтами — это повтор уже прошедшей публикации, и он принимается без
второй загрузки. Воркер недоступен — сборка отказывает, а не угадывает.

**wrangler закреплён** в `apps/proxy` (devDependency) и вызывается через
`pnpm --config.verify-deps-before-run=false exec wrangler`: без этого флага `pnpm exec` ставит
недостающую зависимость перед запуском (проверено 2026-10-03), то есть ходил бы в реестр с
токеном D1 в окружении. Телеметрия wrangler выключена (`WRANGLER_SEND_METRICS=false`).

## Агент обновления

```bash
pnpm feed:agent                                        # чекаут агента, загрузчик, plist, загрузка (только HEAD = origin/main)
node tools/install-feed-agent.mjs --allow-branch       # с другого HEAD или с правками ставящихся файлов: обход ADR-0017; пишется в feed.log и в installedOffMain
node tools/install-feed-agent.mjs --status             # plist, загрузчик и его расхождение с чекаутом, launchd, последний прогон, PR со снимком
node tools/install-feed-agent.mjs --uninstall          # bootout, удалить plist и загрузчик, проверить launchctl print
node tools/install-feed-agent.mjs --uninstall --purge  # и чекаут, состояние, логи
```

- **Что запускает launchd:** строку `/bin/sh`, которая запускает загрузчик
  `~/.okolos/bin/feed-agent/bootstrap.mjs` (копию `tools/feed/bootstrap.mjs` и шести модулей,
  которые он импортирует: пять из `tools/feed/`, а `is-main.mjs` из `tools/is-main.mjs`; список
  в `BOOTSTRAP_SOURCES`), а не `cd` в чекаут (B-159). С 2026-10-09 по 2026-10-26 чекаута не было,
  каждый запуск падал в оболочке, статус не писался и `consecutiveFailures` оставался 0 (B-149).
  Загрузчик проверяет чекаут; отсутствующий пересоздаёт на `origin/main` (worktree клона, из
  которого ставили агента, после `git worktree prune`; если клона нет, `git clone` его origin),
  сломанный сначала переносит в `~/.okolos/agent-checkout.broken`. Затем запускает
  `tools/feed-job.mjs --agent` из чекаута.
- **Что и где записано при сбое.** Каждая строка ниже пишет `outcome: failed` в
  `~/.okolos/state/feed-status.json` и считается в `consecutiveFailures`:
  - `stage: launch`: `node` не найден, копии загрузчика нет, или `node` вышел с ненулевым кодом,
    а статуса с `runId` этого запуска нет. Загрузчик вписывает этот `runId` и в статус, который
    задача записала без него, так что один сбой считается один раз. Пишет сама строка `/bin/sh` из plist (через временный файл и
    `mv`, `lastPublished` сохраняется, `runId` в записи один, её собственный), плюс строка в
    `feed.log` и в `feed.launchd.log`;
  - `stage: checkout`: чекаут не удалось пересоздать или починка не уложилась в срок прогона;
  - `stage: job`: задача умерла, не записав статус; её stderr (ошибка и стек) уходит в `feed.log`
    и `feed.launchd.log`, а `reason` берётся из первой строки с ошибкой. Если задачу убил срок
    прогона, код 124 и `reason` всегда одна фраза: «the run's deadline (2700 s) passed during the job; its process group was killed»;
  - стадии самой задачи (`config`, `pin`, `ingest`, `publish`, сторож, сигнал);
  - загрузчик остановлен сигналом (SIGTERM, SIGINT), а задача не записала статус этого прогона:
    стадия, на которой застала остановка, код 143, `reason: stopped by <signal>`. Починка или
    задача, убитые остановкой, не записываются как падение;
  - `stage: bootstrap`: упал сам загрузчик (стек в `feed.launchd.log`).

  Если агента ставили с `--allow-branch`, каждая из этих записей несёт `installedOffMain`: и
  строки `/bin/sh`, и загрузчика, и задачи, включая остановку сигналом.

  Другой прогон держит блокировку (код 75): статус не пишется, он принадлежит идущему прогону.
  Нигде не записано: launchd вообще не запускает агента (plist нет, агент выгружен или отключён)
  или не стартует сам `/bin/sh`; это видно только в `--status` и `launchctl print`.
- **После слияния B-159, один раз, руками.** Пока агента не переустановили, Mac запускает старый
  plist с `cd` в чекаут. Из основного клона на `origin/main`:

  ```bash
  pnpm feed:agent
  node tools/install-feed-agent.mjs --status   # "bootstrap": true, "plistStartsBootstrap": true, "loaded": true
  plutil -extract ProgramArguments.2 raw -o - ~/Library/LaunchAgents/app.okolos.feed.plist
  # строка должна называть ~/.okolos/bin/feed-agent/bootstrap.mjs
  ```

  B-159 закрывается только после этой проверки.
- **Откуда ставить.** `pnpm feed:agent` ставит агента, только если HEAD клона равен только что
  полученному `origin/main` (сверяется коммит, не имя ветки) и файлы, которые установщик берёт из
  рабочего дерева (исходники загрузчика и шаблон plist, `INSTALLED_SOURCES`), совпадают с HEAD:
  без правок, индекса, удалений и неотслеживаемых файлов. Иначе отказ одной строкой с именами
  файлов. `--allow-branch` обходит отказ; запись об этом, с именами файлов, уходит в `feed.log` и
  в `installedOffMain`.
- **Где работает:** собственный чекаут `~/.okolos/agent-checkout` на `origin/main`: worktree
  клона, из которого ставили агента, или, если того клона нет, клон его origin. Перед каждым
  прогоном агент перематывает его на `origin/main` и, если сдвинулся lockfile, ставит только
  инструменты публикации. Загрузчик обновляется только переустановкой: после изменения
  `tools/feed/bootstrap.mjs` или его модулей на `main` снова `pnpm feed:agent`; `--status`
  показывает расхождение (`bootstrapMatchesCheckout`, `bootstrapDiffers`). Ручной
  `pnpm feed:refresh` из клона не на `origin/main` отказывает; `--unpinned` — аварийный обход, он
  записывается в статус.
- **Когда:** каждые 12 часов и при входе в систему; при входе прогон смотрит на возраст
  отданного фида и, если тот моложе 11 часов, записывает «skipped» и выходит.
- **Снимок в дереве (B-158).** Гейт выпуска (`pnpm package:check`, и CI на `main`) отказывает, когда
  `feeds/phishing.json` старше 14 дней (`FEED_MAX_AGE_DAYS` в `tools/feed-age.mjs`). Поэтому прогон,
  который опубликовал фид (`--snapshot-pr`, входит в `--agent`), смотрит на снимок в `origin/main`.
  Если тому 7 дней или больше (возраст сравнивается без округления) и его версия ниже
  опубликованной, прогон:
  1. сверяет, что `update`, который отдаёт воркер (он отдаёт фид подписанным, `{update, signature}`),
     равен фиду, опубликованному с этой машины, и берёт сам файл
     `~/.okolos/state/feeds/phishing.json` (без подписи, `{kind, body}`) с переводом строки в конце,
     как `pnpm feed:snapshot`;
  2. строит коммит, который меняет только `feeds/phishing.json`, от дерева `origin/main`, через
     отдельный индекс во временной папке: HEAD, индекс и файлы чекаута агента не меняются;
  3. пушит его в одну и ту же ветку `chore/feed-snapshot-auto`, без force. Новый коммит всегда
     потомок вершины ветки (если `main` ушёл вперёд, это коммит слияния с `main`), так что пуш
     всегда fast-forward и PR не отстаёт от `main`. Ветку, в которой есть что-то кроме снимка,
     агент не трогает и пишет причину. Пуш идёт с `OKOLOS_SKIP_GATES=1`: в чекауте агента стоят
     только инструменты публикации, восемь гейтов там не запустить. Вывод пуша построчно уходит в
     `feed.log`, так что там остаётся строка хука `pre-push: SKIPPED by OKOLOS_SKIP_GATES: …`;
     гейт этого коммита это проверки PR;
  4. открывает PR в `main` или обновляет открытый (заголовок и текст называют версию) и просит
     GitHub слить его коммитом слияния, когда обязательные проверки `main` зелёные:
     `gh pr merge <n> --auto --merge --match-head-commit <commit>`. Не просит, если в репозитории
     выключено автослияние или правила `main` не требуют ни одной проверки (тогда автослияние
     слило бы до CI). Руками и с правами администратора агент не сливает никогда.

  Итог в статусе, поле `snapshotPr`: `outcome` один из `skipped-fresh`, `updated` (PR обновлён,
  автослияние на нём уже включено), `auto-merge-requested`, `auto-merge-unavailable`, `failed`, с
  `reason`; открыт PR или обновлён, говорит `pr.action` (`opened`, `updated`). Рядом `branch`,
  `version`, `committed` (версия и возраст снимка на `main`), `commit`, `pr` (`number`, `url`,
  `action`), `at` (когда шёл шаг) и `since` (с какого прогона этот PR ждёт). Последний шаг лежит в
  `~/.okolos/state/snapshot-pr.json` (`0600`) и переносится в каждую следующую запись задачи, пока
  его не заменит новый шаг: прогон «skipped» при входе или упавший в стадиях задачи прогон его не
  стирают. Записи загрузчика и строки запуска (`stage: checkout`, `job`, `launch`) его не несут, но
  файл остаётся, и следующая запись задачи возвращает поле; `--status` читает файл. В
  `feed.log` одна строка `snapshot PR: …` (и строки пуша). Сбой этого шага не делает прогон
  неудачным: `outcome` остаётся `published`, `lastPublished` сдвигается, `consecutiveFailures` не
  растёт. Остановка сигналом (SIGTERM, SIGINT) во время шага тоже: запись `published`, а в
  `snapshotPr` `failed` с `reason: stopped by <signal>`; после остановки шаг не запускает больше ни
  одного процесса, а в `snapshot-pr.json` остаётся последний законченный шаг. gh не установлен или
  не вошёл в github.com: `failed`, `reason` начинается с `gh unavailable`. gh работает на своём
  сохранённом входе (`gh auth login` один раз, человеком); `GH_TOKEN`, `GITHUB_TOKEN` и токен
  Cloudflare из окружения git и gh убираются. Сроки: git 90 с, gh 60 с, весь шаг 5 минут и не
  дольше, чем оставляет сторож прогона. Установленный загрузчик это не меняет: переставлять агента
  не нужно.

  **Где видно, что PR ждёт.** `node tools/install-feed-agent.mjs --status` печатает `snapshotPr` и
  в `note` строку «snapshot pull request #N (ссылка) waits for a person since <время>». Больше
  этого не скажет никто: PR открыт от имени владельца входа gh, а GitHub не присылает автору
  уведомлений о его собственном PR; `feed-status.json` пока не читает ни одна тревога (OBS-32).
  Под launchd пуш и gh ещё ни разу не наблюдались: первое свидетельство будет `snapshotPr` в
  `--status` после первой публикации позже 2026-11-02T21:08Z.

  **Пока оператор не решил B-186, каждый такой PR ждёт человека.** На 2026-10-29 в репозитории
  выключено автослияние (`gh api repos/passioncode-ai/okolos --jq .allow_auto_merge` печатает
  `false`), а в наборе правил `protect-default-branch` только `deletion` и `non_fast_forward`, без
  обязательных проверок; агент пишет `auto-merge-unavailable`. На `main` снимок v65 с
  `body.updatedAt` 2026-10-26T21:08Z, так что первый PR придёт с первой публикацией позже
  2026-11-02T21:08Z (если это изменение к тому времени на `origin/main`), а `main` покраснеет в
  2026-11-09T21:08Z, если PR не слить. Что делать человеку:
  - **сливать коммитом слияния** («Create a merge commit»), когда CI на PR зелёный, не squash и не
    rebase, хотя репозиторий разрешает и их. Ветка агента одна на все PR: только коммит слияния
    делает её коммиты предками `main`, и следующий PR начнётся с `main` без них. После squash или
    rebase старые коммиты ветки в историю `main` не попадают, и каждый следующий PR несёт их снова
    (под коммитом слияния с `main`; меняется по-прежнему только снимок);
  - **снимок закоммичен руками, пока PR агента открыт:** оба меняют `feeds/phishing.json` от одной
    старой базы, PR агента остаётся с конфликтом и с заголовком о старой версии, а агент вернётся к
    нему только через 7 дней (снимок на `main` снова свежий). Такой PR закрыть руками; ветку можно
    оставить, агент продолжит её следующим коммитом поверх;
  - **нет PR** (в `--status` `failed`, `gh unavailable` или отклонённый пуш, или к восьмому дню
    снимка на ветке `chore/feed-snapshot-auto` нет открытого PR): по-старому, `pnpm feed:snapshot` в
    клоне на `origin/main`, коммит одного `feeds/phishing.json` в отдельной ветке и PR в `main`.

  **Чтобы PR сливался сам** (это и есть решение B-186), нужны два изменения настроек репозитория,
  администратором, один раз: включить «Allow auto-merge» (`allow_auto_merge`) и добавить в
  `protect-default-branch` обязательную проверку статуса (задания CI из `.github/workflows/ci.yml`).
  **Побочное действие второго:** у набора правил нет обходящих (`bypass_actors` пуст), поэтому
  GitHub начнёт отказывать в любом прямом пуше в `main`, чей коммит не прошёл проверки: изменения,
  включая снимок руками, пойдут в `main` только через PR, если не добавить обходящего.
- **Границы:** каждая стадия — дочерний процесс в своей группе с дедлайном. Один срок на весь
  прогон, починка чекаута включительно: 45 минут от старта загрузчика. Починка, не закончившаяся к
  сроку, прерывается и записывается (`stage: checkout`, код 124); сторож задачи равен остатку минус
  2 минуты, но не больше её 30 минут; в срок загрузчик убивает группу задачи. Худший случай:
  45 минут и 5 с на завершение. Починка сама длится не дольше 21 минуты (путь через клон). Один
  прогон за раз (`~/.okolos/state/feed.lock`, общий с ручным запуском); три попытки с паузами
  30 с и 2 мин.
- **Где смотреть:** лог `~/Library/Logs/Okolos/feed.log` (5 × 5 МБ, `0600`), статус
  `~/.okolos/state/feed-status.json`: `outcome`, `stage`, `exit`, `version`, `entries`,
  `consecutiveFailures`, `lastPublished`, `recoveredCheckout` (`true`, если перед прогоном
  чекаут пришлось пересоздать; `recovery` говорит, что с ним было), `installedOffMain` (агента
  поставили в обход проверки origin/main), `snapshotPr` (PR со снимком, выше). Две неудачи подряд или
  `lastPublished` старше 26 часов — повод разбираться. **Внешней тревоги пока нет:**
  `feed-status.json` никто не читает. Тревога заведена как OBS-32 в
  `passioncode-ai/project-observatory-dashboard` (B-135 закрыт: он её завёл), и этот файл она пока
  не читает. Смотрит человек, через
  `--status`. `recoveredCheckout: true` значит, что чекаут кто-то удалил: ищите, кто (B-150).
- **Токен** получает только стадия публикации: раннер секрета (`OKOLOS_SECRET_RUNNER` в plist,
  argv без значения) оборачивает её одну. `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_API_KEY`
  убираются из окружения всех остальных дочерних процессов задачи, загрузчика и установщика
  (один список, `SECRET_VARIABLES` в `tools/feed/bounded.mjs`; каждый дочерний процесс
  установщика, git, pnpm, launchctl и поиск Observatory, идёт через `installerTool` или
  `installerRun` в `tools/install-feed-agent.mjs`). Исключение одно: загрузчик отдаёт самой
  задаче окружение целиком, потому что публикация наследует его через неё.

Входной файл — обновление без подписи:

```json
{ "kind": "snapshot",
  "body": { "name": "phishing", "version": 1, "updatedAt": "2026-08-08T00:00:00.000Z",
            "entries": ["evil.test"] } }
```

Одна команда намеренно: **таблица фидов оставалась пустой именно потому, что
публикация была фразой в раннбуке.** Шаг, который делают руками, — это шаг,
который пропускают, когда поздно. Инструмент подписывает через
`tools/sign-feed.mjs` (не переписывая его), проверяет подпись **тем ключом,
который уедет в сборку**, кладёт в D1 и в конце скачивает опубликованное с
воркера, сверяя байт в байт.

**Воркер не подписывает никогда.** Приватная половина ключа на сервер не
попадает: он отдаёт ровно то, что было опубликовано, и любое изменение по пути
провалило бы проверку в расширении — в этом и смысл.

**Публикация пишет обе таблицы.** `feeds` — то, что скачивает и на чём
блокирует расширение; `listings` — то, из чего отвечает публичная страница
статуса. Написанные порознь, они разошлись: воркер отдавал фид с четырьмя
доменами и о каждом из них отвечал владельцу «ничего не записано». Теперь это
один SQL-файл и одна операция, а смоук в конце спрашивает страницу о первом
домене фида и требует ответа `listed` — публикация, которая не может ответить
за опубликованное, не закончена.

Правила, которые держит `tools/listings.mjs` (тесты — `tools/listings.test.ts`):
снимок выметает то, что фид больше не несёт, дельта не трогает то, о чём молчит;
листинг заводится по хосту, даже если запись сужена путём; `entry_date` — дата,
а не мгновение, и она не переписывается при переиздании, потому что её цитирует
владелец.

**Версию надо повышать.** Расширение отвергает обновление, которое не новее
того, что уже в силе (`not-newer`), — это защита от повтора, а не придирка.
