# Разработка — раннбук

Как поднять, собрать, прогнать и выпустить. До этого документа знание жило в
`CLAUDE.md` и в голове; в голове оно хранится ровно до первой смены человека.

Каждая команда ниже исполнима как записана, и это держит гейт
`tools/runbook.test.ts`: он берёт команды из этого файла и требует, чтобы скрипт
или файл существовал. Он же проверяет обратное — что ни один скрипт из
`package.json` не остался здесь неназванным. Возможность, о которой никто не
знает, отличается от отсутствующей только тем, что за неё уже заплатили.

## Что нужно на машине

| Что | Версия | Зачем |
|---|---|---|
| Node | `>=22` (проверено на 26.4.0) | всё остальное |
| pnpm | `11.10.0` — задан в `packageManager` | воркспейс из 21 пакета |
| Python 3 | любой 3.x (проверено на 3.14.6) | `docs/ux/lint.py`, `tools/model/evaluate.py` |
| Браузеры Playwright | ставятся командой ниже | e2e в Chromium и Firefox |

Corepack включит нужный pnpm сам:

```bash
corepack enable
pnpm install
pnpm exec playwright install chromium firefox
```

`pnpm install` попутно ставит хук: `prepare` переводит `core.hooksPath` на
`.githooks`, и с этого момента `git push` не уходит без гейтов. Это не
формальность — 2026-08-07 красный коммит ушёл именно потому, что правило жило в
документе, а push в шелле.

## Цикл разработки

```bash
pnpm test:watch        # то, что крутится в соседнем окне
pnpm test              # весь юнит-прогон, секунды; читает dist/ — на свежем клоне сначала pnpm build
pnpm typecheck         # tsc -b по проектам + отдельный проект для тестов
pnpm lint              # eslint по всему дереву
pnpm build             # dist/chrome и dist/firefox
```

Перед пушем всё сразу — той же командой, что гоняет CI:

```bash
pnpm gates             # lint → typecheck → build → test → ux:lint → brand:lint → i18n:sweep → package:check
```

`pnpm gates` — это `&&`-цепочка: первый упавший шаг останавливает остальные, и
это намеренно. Цепочка через `;` печатает четыре отчёта, из которых читают
последний.

## Тесты, которые не входят в `gates`

Они дороже и требуют браузеров, поэтому в CI живут отдельными задачами:

```bash
pnpm test:e2e          # сборка + сборка с хуками + playwright (Chromium)
pnpm test:e2e:firefox  # geckodriver + selenium, установка расширения в Firefox
pnpm bench             # бенчмарки горячих путей, vitest
```

**Что меряет `pnpm bench` и чего он намеренно не делает.** Два файла:
`packages/core-injection/src/stage1.bench.ts` (первая ступень над страницей в 50
и 1000 кандидатов) и `packages/core-feeds/src/rules.bench.ts` (сборка блокирующих
правил из фида в 2000, 5000 и 10000 записей, с исключениями и без). До 2026-08-20
файлов `*.bench.*` в дереве не было вообще, и команда всегда выходила с кодом 1 —
а команда, которая всегда красная, учит себя пропускать (B-49).

**Он сообщает, а не гейтит, и это решение.** Потолок по настенным часам в CI —
это флейк: та же причина, по которой из цепочки гейтов исключены `suffix:gap` и
`graph:check`. Бюджет, который чувствует человек, держит `e2e/budget.spec.ts` в
браузере, а память воркера — `e2e/memory.spec.ts`. Бенч отвечает на вопрос, на
который они ответить не могут: какой из горячих путей стал медленнее между двумя
коммитами на одной машине.

Первый же прогон это и показал: сборка правил с **пятьюдесятью** исключениями
стоила 20 мс против 4.9 мс без них — вчетверо дороже всей сборки, потому что
`trustedUnder` разворачивал всё множество исключений на каждое из 5000 правил.
Теперь это индекс, который строится один раз: 5.4 мс, то есть исключения
перестали стоить.

`pnpm test:e2e` собирает **две** сборки: обычную и `dist/<target>-e2e` с
открытыми shadow-корнями. Вторую можно собрать отдельно:

```bash
pnpm build:e2e         # dist/chrome-e2e и dist/firefox-e2e, shadow-корни открыты
pnpm public:style      # apps/proxy/src/style.generated.ts из packages/ui/src/tokens.ts
```

**Публичные страницы носят стиль в себе, и он сгенерирован.** У воркера нет ни сборки CSS, ни
файловой системы в рантайме, поэтому лист собирается из `packages/ui/src/tokens.ts` в
`apps/proxy/src/style.generated.ts` (`pnpm public:style`) и встраивается в `<head>` всех трёх
страниц. Рисованная от руки палитра здесь была бы вторым местом, где живёт цвет; тест сверяет
файл с генератором, как это уже делает `tokens.test.ts` для расширения. До 2026-08-21 у всех
трёх страниц не было ни одного правила стиля — разметка, тексты и метаданные были верны, и
именно поэтому ни один гейт этого не замечал: они читают структуру, а не смотрят.

**Ожидание поверхности идёт через `e2e/surfaces.ts`, и это правило гейта.**
`expect(locator).toHaveCount(1)` на баннере печатает «74 × locator resolved to 0
elements» и больше ничего, а между навигацией и баннером пять звеньев: расширение
загрузилось, воркер поднялся, контент-скрипт выполнился, вердикт получился, RPC
вернулся. `expectSurface(page, selector, context)` делает то же утверждение с тем же
бюджетом и при падении печатает, какое звено порвалось. Класс стоил трёх красных
прогонов CI (B-65 дважды, B-108 один раз), каждый раз из файла без отчёта;
`tools/surface-waits.test.ts` теперь отказывает ручной форме. Отчёт читает **обе стороны**:
страницу (`okolos:collect`, `okolos:scan-failed`, `okolos:scan-blinded`, `okolos:scan-partial`,
`okolos:banner`) и воркер (`okolos:verdict` — получил ли фон вопрос и ответил ли, и сколько
воркер живёт). Это разделяет три случая, которые со страницы выглядят одинаково: сообщение не
дошло до воркера, воркер взял и не ответил, ответил и ответ потерялся. Правило на будущее —
`tools/marks-read.test.ts`: метка, которую продукт пишет, обязана читаться отчётом. Оно
завелось на двух настоящих пробелах (`okolos:scan-partial`, `okolos:banner`), а класс — самый
дорогой в B-78: ответ лежал на странице, и никто его не спрашивал.

**Спека не навигирует раньше, чем расширение зарегистрировано.** Ожидание воркера —
в фикстуре `context` обоих харнессов, одно определение в `e2e/ready.ts`. До
2026-08-21 оно жило в фикстуре `extensionId`, и четырнадцать спек её не просили:
вкладка, открытая до регистрации, не получает контент-скрипт ни тогда, ни позже.
Единственное исключение — `cold-start.spec.ts` с опцией `coldWorker: true`, потому
что прогретый воркер — ровно то, чего этому файлу нельзя.

**Запустить спеку против устаревшей сборки нельзя.** Харнессы читают **разные**
каталоги: `e2e/hooks.ts` — `dist/chrome-e2e`, `e2e/fixtures.ts` — `dist/chrome`,
и спеки делятся между ними примерно пополам. `pnpm build:e2e` обновляет только
первый, поэтому «я пересобрал» и «сборка под этой спекой свежая» были двумя
фактами в одной фразе: плант «кнопка удаляет с первого клика» остался зелёным на
трёх проверках `scn-023`, потому что они читают другой каталог (B-42). Теперь
каждый харнесс перед запуском браузера сверяет время сборки с самым свежим
входом сборки (`tools/build-age.mjs`) и отказывается с командой, которую надо
набрать. У Firefox-харнесса был тот же класс в мягкой форме: он спрашивал
`existsSync` — то есть «есть», а не «свежая».

В магазин уходит только первая; `pnpm package` отказывается паковать вторую, и
это проверка, а не соглашение — закрытый корень и есть граница доверия
([ADR-0001](../adr/0001-closed-shadow-root.md)).

Firefox-прогон ищет бинарник в кэше Playwright, иначе — `FIREFOX_BINARY`. Он
поднимает geckodriver на порту 4444; занятый порт — самая частая причина
непонятного падения.

## Генерируемое — руками не править

Восемь артефактов собираются из источника. Правка результата вместо источника
живёт до следующей генерации, а гейт ловит расхождение раньше:

```bash
node tools/icons.mjs         # apps/extension/icons/*.png
node tools/tokens.mjs        # apps/extension/src/tokens.generated.css
node tools/privacy-page.mjs  # страница /privacy воркера из docs/privacy.md
pnpm wireframes              # docs/ux/wireframes/*.md из рендереров
pnpm screenshots             # docs/store/screenshots/*.png
```

Источники — `packages/ui/src/tokens.ts`, `docs/privacy.md`, сами рендереры.
Решение, почему это генерируется, а не дублируется, записано в
[ADR-0007](../adr/0007-generate-what-would-drift.md).

Туда же относится и измерение:

```bash
pnpm i18n:sweep              # входит в gates: отказывает, если фраза мимо каталога
pnpm feed:ingest             # собрать блок-лист из OpenPhish в ~/.okolos/state/feeds/phishing.json
pnpm feed:refresh            # собрать и опубликовать одной командой (ключ подписи, чекаут на origin/main)
pnpm feed:agent              # поставить launchd-агента: обновляет фид каждые 12 часов
pnpm feed:snapshot           # скопировать опубликованный фид в feeds/phishing.json — для коммита
node tools/i18n-sweep.mjs --list   # каждая, с файлом и строкой
```

Свип появился потому, что число четыре итерации подряд выводилось новым
одноразовым регэкспом — и все четыре раза занижало: шаблон требовал заглавной
первой буквы, а строки журнала отправок начинаются со строчной. Измерение,
изобретаемое каждый прогон, — догадка в одежде числа.

## Выпуск

```bash
pnpm package         # собирает, проверяет, кладёт zip и печатает размер и sha256
pnpm package:check   # те же проверки, без записи архива
```

Архивы уходят в `apps/extension/dist/release/okolos-<target>-<version>.zip`.
Упаковка отказывается от сборки с тестовыми хуками, от манифеста, называющего
отсутствующий файл, и от локали, не отвечающей на `__MSG__` из манифеста.
После каждого архива она сама удаляет старые: остаются текущий и предыдущий на
браузер (LC-15, `tools/release-prune.mjs`, тест `tools/release-prune.test.ts`).

Прокси и подпись фидов — свои раннбуки:
[worker-deploy.md](worker-deploy.md), [feed-signing.md](feed-signing.md).

```bash
pnpm graph:check     # висячие рёбра в графе кода
```

## Доступы

Всё, что нужно для деплоя и публикации, записывается один раз и проверяется
одной командой:

```bash
pnpm access:list                             # что есть, что работает, что это разблокирует
pnpm access:check                            # ненулевой код, если чего-то нет или сломано
printf %s "$VALUE" | node tools/access.mjs set CLOUDFLARE_API_TOKEN
node tools/access.mjs permissions            # правила для ~/.claude/settings.json
```

**Двоеточие в имени — не стиль, а условие работы.** Скрипт назывался `access`, и
`pnpm access` до `tools/access.mjs` не доходил никогда: pnpm отвечает своей
`ERR_PNPM_NOT_IMPLEMENTED` раньше, чем смотрит на скрипты. Инструмент работал,
раннбук документировал форму, а `tools/runbook.test.ts` **требовал** её
документировать — гейт настаивал на документации команды, которая не запускается,
и красным при этом не было ничего. У команд pnpm двоеточия нет ни в одной, поэтому
namespaced-имя перехватить нельзя; одиночные слова разрешены только там, где
пересылка **измерена** (`tools/script-names.test.ts`, с канарейкой, которая
проверяет сам список).

**Проверяется годность, а не наличие.** Токен спрашивается тем, для чего он
нужен — доступ к аккаунту и к базе D1; приватный ключ сверяется с публичной
половиной, вкомпилированной в расширение. Первая версия проверки звала
`/user/tokens/verify` и объявила рабочий токен недействительным: этот эндпоинт
не отвечает на account-scoped токены. Проверка, отправляющая ротировать
исправный ключ, хуже отсутствующей.

**Значение не появляется в командной строке.** `set` читает stdin: argv попадает
в историю шелла и в таблицу процессов. Инструмент не печатает значений — ни при
успехе, ни в ошибке.

| Где | Что | Режим |
|---|---|---|
| слот `okolos/prod/CLOUDFLARE_API_TOKEN` в хранилище Project Observatory | токен публикации фида: D1 Write на один аккаунт. Выпускается `cloudflare.py issue --preset d1-edit --account <slug> --vault okolos/prod/CLOUDFLARE_API_TOKEN`, агент берёт его через `use_secret.py`, если Observatory стоит на машине | хранилище |
| `~/.okolos/cloudflare.env` | токен (запасной путь без Observatory), id аккаунта, id базы D1, адрес воркера | `0600` |
| `~/.okolos/tools.env` | `GEMINI_API_KEY` для семантики графа | `0600` |
| `~/.okolos/feed-signing-key.pem` | приватная половина Ed25519 | `0600`, каталог `0700` |

Ничего из этого в дерево не попадает, и это проверяется **содержимым** файлов, а
не их именами. Воркер не подписывает фиды никогда —
[ADR-0002](../adr/0002-worker-never-signs.md).

**Гейт харнеса — отдельная история, и кредами он не снимается.** Прод-мутирующая
команда гейтится как решение о правах, а решение принимает человек:
`node tools/access.mjs permissions` печатает точные строки для
`~/.claude/settings.json` и на этом останавливается.

## Когда гейт упал

- **`pnpm test` красный, а причина неочевидна** — гейты этого проекта пишут в
  сообщение то, что нашли, а не «expected true to be false». Читайте строку
  целиком.
- **e2e висит на установке фикстуры** — почти всегда браузер не принял пакет
  целиком. `e2e/loads.spec.ts` отвечает именно на этот вопрос и падает первым.
- **pre-push не пускает** — это и есть его работа. Обход существует
  (`OKOLOS_SKIP_GATES=1 git push`) и печатает, что именно не проверено;
  `--no-verify` не оставляет следа и потому не рекомендуется.
- **Аренда agent-sync или удаление ветки не ждут гейтов.** pre-push читает со stdin, какие
  ref-ы уходят, и гоняет гейты, только когда ветка или тег получают содержимое. Push одних
  `refs/agent-sync/leases/*` или удаление ветки проходит сразу, с одной строкой об этом.
  Ручной запуск хука без stdin проверяет всё. Правило держит `tools/ci.test.ts`
  («decides from what is pushed»).
- **Под большой нагрузкой машины** гейты не падают по часам: сборка в `bundle-scan`
  асинхронная, а `testTimeout` — 30 с (`vitest.config.ts`). Если тест всё же упал по
  таймауту, это зависание, а не медленная машина.

## Прочее

```bash
pnpm ux:lint         # структура docs/ux, входит в gates
pnpm brand:lint      # бренд-пак против brand-contract v1, входит в gates
pnpm graph:check     # граф кода: висячие рёбра, свежесть, рост сирот
pnpm suffix:gap      # таблица суффиксов против настоящего Public Suffix List
```

**Форматтера в этом репозитории нет, и это решение.** До 2026-08-20 здесь стоял
`pnpm format` (`prettier --write .`) **без конфигурации prettier** — то есть команда,
переписывающая дерево в дефолтный стиль prettier: двойные кавычки, точки с запятой,
ширина 80. Кодовая база написана иначе, и это не вопрос вкуса, а измерение: при
самых близких к фактическому стилю настройках (`--single-quote --no-semi
--print-width 100`) расходятся **175 файлов из 402**. Prettier этот стиль не
воспроизводит, поэтому «завести конфиг и отформатировать один раз» означало бы
переписать сорок четыре процента файлов — и заодно сдвинуть все ссылки `file:line`,
на которых стоит документация этого проекта.

Стиль держит `pnpm lint` (eslint). Отдельный прогон одного файла тоже не нужен:
`prettier --write <файл>` раскрывает объекты в многострочные, а повторный прогон их
**не сворачивает** (`objectWrap: preserve` — дефолт с prettier 3.5), то есть правка
необратима форматированием. Проверено на `apps/extension/src/content/index.ts`:
файл пришлось восстанавливать из HEAD. Возврат prettier'а ловит
`tools/scripts-do-what-they-say.test.ts`.

**Почему `suffix:gap` не в `gates` — та же причина, что у `graph:check`.** Он тянет
список с `publicsuffix.org`, и гейт, зависящий от внешнего адреса, краснеет в тот
день, когда у этого адреса плохой день — класс флейка, который этот проект
отказывается терпеть. Запускается осознанно, как пересборка графа, и печатает четыре
числа, на которых стоит решение в `suffixes.json`: сколько правил в настоящем списке,
сколько у нас, сколько находок теряется на настоящем фиде и сколько платформ
заблокировал бы неизвестный приватный апекс. Локальную копию можно передать
аргументом: `pnpm suffix:gap public_suffix_list.dat`.

**Почему `graph:check` в `gates` нет.** `graphify-out/` в `.gitignore`, на свежем
клоне и в CI его нет вообще, а гейт, который на отсутствие артефакта отвечает
«ок», — это ровно та форма, где отсутствие данных читается как проход. Поэтому он
отказывает и на отсутствие, и на устаревание, и запускается там, где граф есть:
после `/graphify`. Это записано и проверяется тестом, чтобы никто не «починил»
несоответствие, добавив в цепочку шаг, который молча пропускает.

**Чем пересобирается граф, и почему это не одна команда.** У CLI `graphify` команд
`build`/`update` нет (`graphify --help` → `install`, `uninstall`, `path`, `explain`,
`diagnose`) — граф строит агентский скил `/graphify . --update`, и извлечение у него
**в два прохода**:

- **AST по коду** — детерминированный, без LLM и без ключа. Идёт всегда и обновляет то,
  ради чего граф читают на стадии 9: кто что вызывает и что сломается при переносе.
- **Семантический по документам и картинкам** — нужен LLM. Либо `GEMINI_API_KEY` /
  `GOOGLE_API_KEY` в окружении, либо хост, который рассылает субагентов. Без этого проход
  не идёт, и graphify **намеренно** оставляет такие файлы без `semantic_hash` в
  `graphify-out/manifest.json`, чтобы следующее обновление их подобрало.

Отсюда правило `pnpm graph:check`: свежесть спрашивается **у манифеста, по каждому
источнику**, а не по времени записи `graph.json`. Проход только по коду перезаписывает
файл графа — и все источники становятся старше артефакта, то есть проверка по времени
отвечает «ничего не менялось» поверх документов, прочитанных двенадцатью днями раньше
(измерено 2026-08-20). Гейт называет три состояния отдельно, потому что расшиваются они
по-разному: `awaiting meaning` — нужен LLM, `changed since` и `never extracted` — хватит
прогона обновления.

**Почему `brand:lint` — обёртка, а не прямой вызов.** У `docs/brand/lint.py` три
кода: 0 чисто, **1 только предупреждения**, 2 любая ошибка. Проводка напрямую
отказывала бы в пуше из-за предупреждения — а проект, чьи гейты отказывают из-за
предупреждений, выучивает `OKOLOS_SKIP_GATES=1`. `tools/brand-gate.mjs` держит это
отображение в файле с причиной, а не трюком с `$?` в строке package.json.
